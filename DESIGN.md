# Nooxit Design System

## Overview

Nooxit is a shadcn/ui-based product system for agentic interfaces. Its visual
reference is a trustworthy technical console rather than a colorful SaaS
marketing surface: warm black and off-white carry most of the interface, and
color becomes visible when it communicates state, risk, success, warning,
selection, or active agent work.

The operating model is **spot a status → intervene → complete a manual UI
process**. The interface should stay visually quiet until the system has
something consequential to say. Controls, navigation, cards, tables, and forms
recede into a neutral scaffold. Status and action feedback get the strongest
chromatic signal.

This is a working library, not a speculative visual language. It ships as the
npm package `nooxit-design-system`: 61 components, 79 color primitives, 64
semantic tokens and 99 text styles.

### Source-of-truth chain

1. The **Figma UI kit** (file `ugfobk75w4e1lOotqhXHfO`) defines every token and
   every component's styling.
2. **`packages/ui/tokens/nooxit.tokens.json`** transcribes it. This is the only
   file anyone edits by hand.
3. `pnpm --filter nooxit-design-system tokens` generates
   `src/styles/tokens.css` (the CSS variables and the Tailwind theme) and
   `src/tokens.ts` (typed exports). **Never edit either by hand.**
4. Components consume semantic variables. Primitives are used directly only
   where the kit itself does — avatar fallbacks, descriptive colors, charts.

The front matter above mirrors step 2. If the two disagree, the JSON wins.

## Colors

The base is warm rather than absolute: `base-black` is `#110F0E` and
`base-white` is `#FBFAF9`. That warmth repeats through the gray ramp and keeps
a monochrome interface from feeling sterile.

### Semantic hierarchy

- **Background / foreground** — `#FBFAF9` / `#110F0E` in light mode, reversed in
  dark.
- **Muted surfaces** — `muted` with `muted-foreground` for secondary text,
  placeholders and captions.
- **Cards and popovers** — share the page background in each mode but keep
  distinct tokens so a product theme can diverge later.
- **Primary actions** — neutral black in light mode, off-white in dark. Primary
  is never a brand-color flood.
- **Accent** — orange, reserved for hover and active states on menu items,
  select items and sidebar entries. Pale orange surface with deep orange
  foreground in light mode; reversed in dark.
- **Status** — red destructive, green success, yellow warning. Each has a solid
  pair and a `-muted` pair for quieter alerts and badges.
- **Descriptive** — lime, blue and orange pairs for diagrams, categories, tags
  and agent-work communication. They never replace the neutral action hierarchy.
- **Sidebar** — an independent semantic layer: background, foreground,
  foreground-70, accent, primary, border and ring.

### Hover is a token, not an opacity

Every interactive surface has a paired hover color. Do not darken with opacity.

| Surface | Hover |
|---|---|
| `bg-primary` | `bg-hover-primary` |
| `bg-secondary` | `bg-hover-secondary` |
| `bg-destructive` | `bg-hover-destructive` |
| `bg-destructive-10` | `bg-hover-destructive-20` |
| `bg-success` | `bg-hover-success` |

Outline and ghost buttons hover to `bg-hover-secondary`; menu and select items
to `bg-accent`; navigation and toggles to `bg-muted`.

### Translucent tokens

Six tokens are composed rather than aliased, and each is registered under a
single Tailwind namespace so exactly one utility exists for it:
`bg-muted-40`, `bg-muted-50`, `bg-accent-50`, `bg-destructive-10`,
`border-muted-40`, `border-destructive-50`. Those names are identical to the
Figma ones, so a spec and its implementation read the same.

`bg-muted-40`, `bg-muted-50` and `bg-accent-50` are marked `origin: adjusted`
in the token JSON: Figma stores them as base-white/base-black at 40–50%, which
is invisible against the page background, so the code follows the Figma *code
syntax* (`muted/.4`, `accent/.5`) instead. The kit's raw value is preserved in
`figmaValue`.

### Tailwind's palette is removed

`--color-*: initial` clears it. `bg-blue-500` and `text-slate-900` do not
resolve — the Nooxit `blue` and `gray` ramps replace them. If a color class
silently does nothing, this is why.

## Typography

**Aspekta** carries everything, including codes, table identifiers,
amounts and times. There is no brand monospace: `font-mono` resolves to the
operating system's monospace and is for code samples only, never product UI.

> **Replaced: DM Sans (2026-10-01).** Aspekta replaced DM Sans. It was chosen
> over Overused Grotesk after a side-by-side client review. Aspekta has no
> italic; the browser slants the upright when italic is asked for. The font is
> self-hosted (next/font/local in the docs, `--font-brand`); the package does
> not ship the files yet.

> **Removed: DM Mono (2026-10-01, client decision).** The six DM Mono
> styles (`text-base/leading-6/mono`, `text-base/leading-none/mono`,
> `text-sm/leading-5/mono`, `text-sm/leading-5/mono-semibold`,
> `text-xs/leading-4/mono`, `text-xs/leading-4/uppercase`) are gone from the
> tokens. Each has a sans twin at the same size and line height. Where an
> uppercase label is still wanted, add `uppercase` to a sans style.

Aspekta has proportional digits and no tabular figures (`tnum`), so
`tabular-nums` does nothing. Do not add it; right-align numeric columns so they
share a right edge.

The kit names its text styles `text-{size}/leading-{value}/{weight}`, which
maps one-to-one onto Tailwind utilities. Letter spacing follows the kit:
`tracking-tight` (-2.5%) at 30px and above, `-0.6px` at 20 and 24px, none below.

Sizes run `text-xs` (12px) through `text-9xl` (128px). Fixed line heights are
12, 16, 20, 24, 28, 32, 36 and 40px; display styles use `leading-none`.

Component labels are usually `text-sm` at medium weight. Supporting copy is
`text-sm leading-5` in `text-muted-foreground`. Card and dialog titles are
semibold, 18–24px.

## Layout

A Tailwind-derived 4px rhythm with 2px half-steps and a 1px hairline. Bind
geometry to gap and padding variables rather than literal values.

- Compact controls: 6–8px vertical, 8–12px horizontal padding.
- Standard fields and buttons: 8–10px vertical, 12px horizontal.
- Cards, dialogs, drawers, sheets: 16px or 24px internal padding.
- Lists and menus: 4–8px gaps. Content groups: 12–24px.

Controls share a set of heights so an input, a select and a button line up in
one row: 24, 28, 32, 36, 40, 44 and 48px.

## Elevation and depth

Borders and tonal surface changes do the structural work. Shadows are reserved
for floating content.

- `shadow-md` — popovers, tooltips, menus, command, select menus, chart tooltips.
- `shadow-lg` — dialogs, drawers, sheets, toasts, switch thumbs.
- `shadow-xs` — the active tab, and almost nothing else.
- **Cards have no shadow.** A 1px border defines them.

Focus has two treatments, chosen by what the control is.

**Text-entry fields change their border.** Input, Textarea, Select,
NativeSelect, InputGroup, InputOTP and the Combobox field turn their own 1px
border `primary` on focus. There is no ring outside the field, so nothing grows
or shifts:

```
focus-visible:border-primary
aria-invalid:focus-visible:border-destructive
```

InputGroup and the Combobox chips field react to focus inside them
(`has-[…:focus-visible]` / `focus-within`) rather than to their own focus.
InputOTP slots share border lines, so the active slot paints its left edge,
which is its neighbour's border, with a 1px `shadow-[-1px_0_0_0_var(--primary)]`.

**Every other control keeps the ring.** Buttons, checkboxes, radios, switches,
tabs, toggles, sliders, links and menu triggers have no border to recolor.
A filled black button, for example, would show no visible change. They use:

```
focus-visible:ring-2 focus-visible:ring-primary
focus-visible:ring-offset-2 focus-visible:ring-offset-background
```

Destructive and invalid controls swap `ring-primary` for `ring-destructive`.
Inside the sidebar it becomes `ring-sidebar-ring` with `ring-offset-sidebar`.
No component uses the stock shadcn 3px translucent ring.

> A 1px color change is a weaker focus cue than a 2px ring and falls short of
> WCAG 2.2's AAA focus-appearance guideline (2.4.13). That tradeoff is
> accepted for now.

## Shapes

- `0px` — dividers and table geometry.
- `4px` (`rounded-sm`) — menu items, checkbox, dialog close, chips.
- `6px` (`rounded-md`) — inputs, selects, popovers, menus, toasts.
- `8px` (`rounded-lg`) — cards, alerts, dialogs, tabs track, command.
- `12px` (`rounded-xl`) — drawer top corners.
- `9999px` — **buttons**, badges, switches, slider thumbs, avatars, progress.

All three named radii derive from one `--radius` variable (8px), so changing it
rounds or squares the system at once. The pill group does not use `--radius` —
the pill shape is the most recognisable part of the system and stays fixed.

> The kit was drawn against Tailwind v3, where `rounded-sm` was 2px and
> `rounded` was 4px. In v4 those are `rounded-xs` and `rounded-sm`. The values
> are identical; read a radius off the kit **in pixels**, never by its label.

## Cursors

Everything clickable shows the pointer cursor. This is declared once in
`theme.css` under `@layer base` — covering `button`, `a[href]`, `label[for]`,
`select`, the ARIA interactive roles, and the clickable input types — because
browsers default `<button>` to `cursor: default` and Tailwind's preflight does
not change it. Disabled controls fall back to `cursor: default`; text inputs
keep the I-beam. Never add `cursor-pointer` to an individual component; it is
already handled.

## Component API

The components keep shadcn/ui's API, so anything you know there still applies.
These are the deliberate deviations an agent has to know:

| Component | Deviation |
|---|---|
| `Button` | Pills. `destructive` is a **boolean prop** that recolors any variant, alongside `variant="destructive"`. Sizes `xs \| sm \| default \| lg` plus `icon`, `icon-sm`, `icon-xs`, `icon-xss`. |
| `Input` | `size?: "default" \| "sm"` (40/36px) — this **shadows the native `size` attribute**, which is not forwarded. Focus turns the 1px border `primary`, with no ring. Invalid inputs keep the normal border until focused, then turn it `destructive`. |
| `Table` | `size?: "sm" \| "md" \| "lg"` on `<Table>` sets row height (56/76/96px). `sm` is the default. |
| `Progress` | `size?: "xs" \| "sm" \| "md" \| "lg"`, default `lg`. |
| `Tabs` | `TabsList` takes `variant="line"` for the underline style. |
| `Badge` | `rounded` boolean; `rounded={false}` gives the 6px square badge. |
| `Card` | `size?: "default" \| "sm"` (24/16px padding). `CardTitle` takes `size="lg" \| "md" \| "sm"`. |
| `Avatar` | `size` xxs→2xl and `shape="circle" \| "rounded"`. |
| `Toggle` | Sizes `sm \| default \| lg` = 36/40/44px. |
| `ToggleGroup` | `spacing` defaults to `1` (4px apart). `spacing={0}` joins them. |
| `Sidebar` | 240px expanded, 48px collapsed. |
| `Tooltip` | A popover, not an inverted chip. |
| `Sonner` | Named `Sooner` in Figma. Error toasts carry the kit's Toast destructive colors. |

Icons come from **Phosphor** (`@phosphor-icons/react`, `iconLibrary:
"phosphor"` in `components.json`). Import them from
`@phosphor-icons/react/ssr`, which works in server and client components
alike, and use the `Icon`-suffixed names, e.g. `CaretDownIcon`. Lines are
**1.33px thick at 16px**: icons use Phosphor's regular weight (1px at 16px),
and a rule in `theme.css` adds a same-color outline stroke of 16/3 units to
every Phosphor SVG. It scales with the icon (1px at 12px, 2px at 24px). Do not
switch weights to change thickness; set `weight` only for a deliberate
exception, such as `weight="fill"` on the menu radio dot. Components size icons automatically
(`[&_svg:not([class*='size-'])]:size-4`), so do not add `size-4` yourself.
Mark leading and trailing icons in buttons so padding compensates:

```tsx
<Button>
  <EnvelopeIcon data-icon="inline-start" />
  Email me
</Button>
```

## Working on this repo with an AI agent

Read this section before changing anything.

1. **Import from the package, not a relative path.**
   `import { Button } from 'nooxit-design-system/components/button'`. Inside
   `packages/ui` the components import each other the same way.
2. **Never edit `src/styles/tokens.css` or `src/tokens.ts`.** Edit
   `tokens/nooxit.tokens.json` and run the `tokens` script.
3. **Check Figma before inventing a value.** The kit is the source of truth. If
   a component or a state is not in the kit, say so and propose a value from
   existing tokens — do not guess a hex.
4. **Use semantic tokens, never primitives**, unless the kit itself uses a
   primitive there (avatar fallbacks, descriptive colors, charts).
5. **Do not add `dark:` color overrides.** Every token already has a dark value;
   a `dark:` class means the wrong token was chosen.
6. **Do not add `cursor-pointer`.** The base layer handles it.
7. **Run the checks.** `pnpm typecheck`, `pnpm lint` and `pnpm build` all pass
   on `main` and must keep passing.
8. **The registry is generated.** `registry.json` comes from the component
   sources; edit the components, then run the `registry` script.

## Do's and Don'ts

- **Do** keep the interface neutral and let status, selection, destructive risk
  and active agent work supply the color.
- **Do** bind fills and strokes to semantic variables.
- **Do** preserve light/dark behavior — never paste a resolved light hex into a
  component that should switch modes.
- **Do** use Aspekta for all interface text, identifiers and numbers included.
- **Do** use the existing text styles; their names encode size, line height and
  weight.
- **Do** favor borders and tonal surfaces over extra elevation.
- **Don't** turn orange, blue, lime, green, yellow or red into broad decorative
  page color. They carry semantic or descriptive meaning.
- **Don't** add gradients, glow, glass effects or ornamental shadows.
- **Don't** substitute pure black or pure white for the warm base tokens.
- **Don't** invent spacing values the 4px scale can already express.
- **Don't** mix arbitrary radii.
- **Don't** ship the underscore-prefixed Figma components (`_Block Header`,
  `_Alert`, `_Change Log`) as product UI; they are documentation scaffolding.

## Audit scope

Produced from a read-only traversal of the Figma file: five variable
collections (136 color, 115 float, 2 string variables), 105 text styles, 20 effect styles, 2 grid styles, no
local paint styles. Live Figma variable values are authoritative over the
`variables2json` block on the Readme page, which is a stale snapshot.
